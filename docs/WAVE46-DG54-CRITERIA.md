## §1 判据臂

```
bash $HOME/w46-popup-verify.sh                 # 起 X（Xvfb，自起自收、按 PID 止损）+ 跑应用 + 采帧 + 判
bash $HOME/w46-popup-verify.sh <输出目录> <X display 号>
bash $HOME/w46-popup-verify.sh --analyze <已有输出目录> [<新输出目录>]   # 只算判据：不起 X、不跑应用
bash $HOME/w46-popup-verify.sh --help
```

- 默认输出目录 `$HOME/w46-pv-<时间戳>`、display `:45`；起 X 的方式与 `$HOME/hc-forceopen.sh` **同款**
  （先探 `xdpyinfo`，活着就复用并 WARN，死了才自起 Xvfb）；应用侧 env = `HC_INPUT_DIAG=1`、
  `HC_DROP_OPEN_AT=25`、`WPF_LINUX_CREATE_DIAG=1`。全程**不用** `pkill -f` / `pgrep -f`。
- 采帧：窗口出现 → 静置 → 点导航到「有 ComboBox 那一页」（第 10 项）→ 采 `pre.png`（**打开前**）
  → 等 `[HCIN] FORCE-OPEN` → 采 `post.png`（**打开后**，连拍到相邻两帧 `AE=0` 的**收敛帧**）。
  若 `pre.png` 采到时 `FORCE-OPEN` 已经打过，脚本会打 `HC_PV WARN pre-too-late` ⇒ **该轮读数无效口径**，不许当绿。

### 四条判据（每条都打印**原始读数**，并同时写入 `<out>/VERDICT.txt`）

| 判据 | 内容 | 判据（阈值） | 修前实测 | 来源 |
|---|---|---|---|---|
| **P1** | 弹窗窗口存在且几何合理 | `tree.txt` 里存在含 **`413x274`** 的窗口行（**打印原文行**） | `0x200008 … 413x274+559+356` ⇒ **PASS** | `D-G54` 登记 |
| **P2** | 弹窗**下半区出画** | 色数 `post > 1`（打印 pre/post 两个色数） | `66 → 1` ⇒ **FAIL** | `D-G54` 登记 |
| **P3** | 弹窗下半区**变化量** | `compare -metric AE` **> 20000** | `3779` ⇒ **FAIL** | `D-G54` 登记 |
| **P4** | 全屏变化量（**辅助**，不参与总判） | `compare -metric AE pre.png post.png` **> 40000** | `11630` ⇒ **FAIL** | 新增（供对峙） |

- **总判**：`VERDICT=PASS` ⇔ `P1∧P2∧P3`；缺读数一律 `NOINFO`（**不许当绿用**）；退出码 `0/1/2·3`。
- 阈值常量写在脚本顶部：`P2_MIN_COLORS`（默认 `1`，可用 `HC_PV_P2_MIN_COLORS` **只许加严**）、
  `P3_AE_MIN`（默认 `20000`，`HC_PV_P3_AE_MIN`）、`P4_AE_MIN`（默认 `40000`，`HC_PV_P4_AE_MIN`）。
- `VERDICT.txt` 里 `P1=…`/`P2=…`/`P3=…`/`P4=…` **每行一条 = `PASS/FAIL` ＋ 原始读数**，
  便于把「修前件」与「修后件」的两份 `VERDICT.txt` **逐行对峙比较**。

### 复算命令（不跑应用即可复算，`--analyze` 模式）

```bash
# 修前现场（本波钉死读数的那一档产物）
bash $HOME/w46-popup-verify.sh --analyze $HOME/hc-forceopen-1 $HOME/w46-recalc-prefix
# 等价的手工口径（三条读数逐个复算）
convert $HOME/hc-forceopen-1/pre.png  -crop 413x250+559+380 +repage /tmp/pre.pop.png
convert $HOME/hc-forceopen-1/post.png -crop 413x250+559+380 +repage /tmp/post.pop.png
identify -format '%k\n' /tmp/pre.pop.png /tmp/post.pop.png          # → 66  然后  1
compare -metric AE /tmp/pre.pop.png /tmp/post.pop.png null: ; echo  # → 3779
compare -metric AE $HOME/hc-forceopen-1/pre.png $HOME/hc-forceopen-1/post.png null: ; echo   # → 11630
```

## §3 为什么这么定

### 3.1 为什么量「弹窗**下半区**」而不是整个弹窗

弹窗矩形（`413x274+559+356`）**最上面那 24 px** 在屏幕上与**组合框自己那一行**重叠：
组合框的边框、箭头、焦点框在「打开前/打开后」**本来就会变** ⇒ 若把整块弹窗拿来算 `AE`/色数，
那些像素会**污染**读数，把「内容一像素没画」掩盖成「区域有变化」。所以口径固定为：

```
下半区 = 弹窗矩形去掉顶部 24 行 = -crop 413x250+559+380     # (274-24) x 250 从 (559, 356+24) 起
```

这与 `D-G54` 登记读数（`66 → 1`、`AE=3779`）**完全同口径**。脚本不是把这个 `crop` 写死到死胡同里：
它先从 `tree.txt` 的原文行**派生**几何，派生值与钉死口径不一致时**明确打 `口径漂移` 警告**并继续用派生值。

### 3.2 为什么 P3 是「远大于 3779」而不是「≠ 0」

`3779` 是**纯白块盖住原页面内容**造成的差值（弹窗区域边缘、圆角、抗锯齿），**不是「画了内容」**。
一条真的下拉列表（多行文本 ＋ 选中态底纹 ＋ 分隔线）在下半区（`413x250 = 103,250 px`）里应当是
**几万像素级**的差异 ⇒ 取 `> 20000` 作为「远大于」的下界。**校准读数**见 §5。

### 3.3 为什么 P4 只当辅助

全屏 `AE` 在修前就已经是 `11630`（白块盖住页面 ≠ 0），它**不是「内容出画」的证据**；
修后它必然上升，但上升幅度受「弹窗内容与底层页面偶尔同色」影响 ⇒ 只作对峙参考，**不参与总判**。

## §4 修好后应该看到什么（三条必须**同时**成立）

1. **弹窗下半区色数 > 1**（`P2=PASS`；修前 `= 1`）；
2. **弹窗下半区 `AE` 远大于 `3779`**（`P3=PASS`，阈值 `20000`）；
3. **肉眼可见下拉列表**：留档图 `<out>/pop_post.png`（下半区原尺寸）与 `<out>/pop_post.2x.png`（放大 200%）
   里应当看得到**列表项文本/底纹/选中态**，而**不是**一整块均匀颜色。

> 预期形态（修法 A：不给弹窗窗口加 `WS_EX_LAYERED` ⇒ 走正常呈现腿、以不透明方式出画）：
> 弹窗整块被**不透明**画出来 ⇒ 下半区色数应在**几百**量级（文本抗锯齿），`AE` 应在**几万**量级。
> 已知代价（同 `D-G54` 登记）：弹窗圆角/阴影的 alpha、`Window.Opacity` 丢失 —— 属**已登记限制**，不是判据失败。

## §5 **反面判据**：只把弹窗画成「一整块纯色」会骗过一部分判据

**反例形态**：弹窗窗口被画成**一整块纯色**（例如纯白 `#FFFFFF` 或纯黑）——例如「修法 A 落地了，
但呈现腿把弹窗当成整块不透明底色刷了一遍」这种情况。

| 判据 | 对「一整块纯色」的反应 | 是否被骗 |
|---|---|---|
| `P1` 几何 | 仍 `PASS`（窗口确实在） | **会被骗**（几何对 ≠ 内容对） |
| `P3` 区域 `AE` | **仍可能 `PASS`** —— 纯黑块盖住白色区域 ⇒ 下半区 `AE` 可到 **103,250**（= 整块面积） | **会被骗** ❗ |
| `P4` 全屏 `AE` | **仍可能 `PASS`** —— 见下表校准：`111,101` | **会被骗** ❗ |
| `P2` 下半区**色数** | **`FAIL`** —— 一整块纯色 ⇒ 色数 `= 1` | **不被骗** ✓ |
| 肉眼留档 | **露馅** —— `pop_post.png` 是一块均匀色，看不到任何列表项 | **不被骗** ✓ |

⇒ **必须同时给出「色数」与「肉眼截图留档」两条**：`P2` 负责**机械**地否掉均匀块，
`pop_post.png` / `pop_post.2x.png` 负责让人**看懂**画的是什么。
脚本为此另打三条不参与总判的辅助读数：`AUX_colors_post_lowerhalf`、`AUX_entropy_post_lowerhalf`
（`0` = 整块均匀）、`AUX_flat_block=yes/no`，并打印下半区**颜色直方图前三名**。

### 5.1 极性校准读数（**合成夹具**，不是真修复的读数；只用来验证判据的加减号）

三个夹具都由 `$HOME/hc-forceopen-1` 的同一份 `pre.png/post.png` 合成（`--analyze` 模式跑）：

| 夹具 | 做法 | `P2` 色数 post | `P3` 下半区 `AE` | `P4` 全屏 `AE` | `AUX_flat_block` | 总判 |
|---|---|---|---|---|---|---|
| **修前**（原生） | — | `1` | `3779` | `11630` | `yes` | `FAIL` |
| **平块**（反面） | `-fill black -draw 'rectangle 559,380 971,629'` | `1` | `103250` | `111101` | `yes` | `FAIL` ✓ |
| **有内容**（模拟修后） | 把 `pre.png` 里一块**真页面内容**（`413x250+120+300`）贴到弹窗下半区 | `220` | `50911` | `58762` | `no` | `PASS` ✓ |

**从这张表要读出的两件事**：
① `P3`/`P4` **单独**对「平块」是 `PASS` ⇒ **不能只用 `AE`**（这就是 §5 的要害）；
② `P2` ＋ 肉眼留档把「平块」与「真内容」区分开（`1` vs `220`）。

## §6 两极化对峙用法（修前件 vs 修后件）

```bash
# 修前件（任何一档修前产物目录）与修后件各跑一遍同一条判据，然后逐行对峙
bash $HOME/w46-popup-verify.sh --analyze <修前目录> $HOME/w46-cmp-before
bash $HOME/w46-popup-verify.sh --analyze <修后目录> $HOME/w46-cmp-after
diff <(grep -E '^(P[1-4]|AUX_|VERDICT)' $HOME/w46-cmp-before/VERDICT.txt) \
     <(grep -E '^(P[1-4]|AUX_|VERDICT)' $HOME/w46-cmp-after/VERDICT.txt)
```

`VERDICT.txt` 里另有 `AUX_fp_libwpfwin32.so / wpfgfx_cor3.so / PresentationCore.dll / libwpfwic.so / libSkiaSharp.so`
的 `sha16` ⇒ 对峙时能**证明**「修后件」换掉的是哪一位（同一次对峙里应只有 `shim` / `pc` 变化），
以及 `AUX_force_open=seen open=True`（证明下拉**确实被打开过**，而不是「根本没打开所以没内容」）。

## §7 边界与如实标注

- **判据射程**：只管「弹窗内容**有没有**画出来」这一件事。它**不**判：弹窗圆角/阴影的 alpha、
  `Window.Opacity`（修法 A 的已登记代价）、下拉的交互语义（打开/关闭/焦点 —— 那半条链已由 `D-G50` 单独判过）。
- **本页与脚本都还没在「修后件」上跑过**：修法 A 尚未落地；上表的「有内容」一行是**合成夹具**，
  用来验证判据的加减号，**不是**真修复的读数。修后件必须以**真产物**重跑本文档 §4 的三条。
- **`P2` 阈值按登记口径写死为 `> 1`**：一个块状区域的**抗锯齿边缘**也可能给出 `> 1` 的色数 ⇒
  判读时把 `AUX_flat_block` / `AUX_entropy_post_lowerhalf` / 直方图前三名**一起**看（§5）。
  若要加严，用 `HC_PV_P2_MIN_COLORS`（只许加严，不许放宽到 `0`）。
- **display 复用风险**：若 `:45` 上已经有别的车道的 X，脚本会 **WARN 并复用**（读数可能被污染）。
  要硬失败就设 `HC_PV_REQUIRE_FREE_X=1`。
- **未取到**：修后件的真读数（`D-G54` 修法 A 未落地）；`413x274` 之外的第二形态弹窗（如带滚动的长列表）读数。

## §8 判据补丁（车道 W46I 独立复验后，**必读**）：`P2 ∧ P3` 不可拆

独立复验（`build/MilBridge/W46I-report.md`）实测出**两条判据各有互不重叠的盲区**，单看任一条都会放行假绿：

| 合成形态 | `P2`（下半区色数） | `P3`（下半区 AE） | 谁抓得住 |
|---|---|---|---|
| **A 纯黑块**（弹窗被一块纯色盖住） | **FAIL 色数=1** | PASS AE=103250 | 只有 **P2** |
| **B 纯白块** | FAIL | FAIL 3779 | 两条 |
| **C 原样 = pre**（窗口在、几何对、**一像素不画**） | **PASS 色数=66** | **FAIL AE=0** | 只有 **P3** |
| **真修后**（列表出画） | PASS 66→**152/206 色** | PASS AE=**12220**（阈值须下调） | — |

⇒ **验收口径（写死）**：`P1 ∧ P2 ∧ P3` 三条**同时**成立；且 `P3` 的阈值必须**下调到能抓住 AE=0** 的量级
（`HC_PV_P3_AE_MIN` 建议 `2000`，并把"修前实测 3779"重新标注为**B 形态的值**，不是"未修的基线"），
另外必须叠加**机器判据** `WPFGFX_ROOTDIAG` 的"**从根可达 ≥ 2**"与**肉眼截图留档**（`pop_post.2x.png` 一类）。

**两条采样口径（否则会重演假象）**：
1. `从根可达=57` 是**呈现之后**的稳态；设根后第一次 ROOTDIAG 是 `从根可达=1`（活投影子=0）⇒ 引用时必须写明采样时刻。
2. **只读 stderr 的 `app.log` 会重演"第二条 SetRoot 没进预检"的假象**（`诊断预算用尽（已打 400 条）`）；
   判据必须读 `WPF_LINUX_MIL_LOG` **文件汇**。
3. `w46-popup-verify.sh` 早先把 `HC_PV SETTLE`（post 是否收敛帧）用 `>/dev/null` 丢掉了 ⇒ 已修（保留该行）。
